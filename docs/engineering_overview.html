How the data pipeline works

This page covers the data and software side of EuroGrid-Climate-Dynamics. It shows how cloud reanalysis data and German grid-operator data are pulled from two public services. It then follows that data through one shared dataset contract, into a small local cache, and on to the blocking and renewable-drought diagnostics. The project is in progress, and section 5 shows which phases are done.

2. Why chunk layout decides what gets downloaded

Cloud Zarr stores are read chunk by chunk, so the way a store is chunked sets the real cost of a request. Each store's layout was checked against the live service before any loader was written, and the result is written down with its date in config/settings.yaml.

StoreHow it is chunkedWhat the pipeline does about it
ARCO-ERA5, surface fieldsOne hour × the whole globe (1 × 721 × 1440)A small European box saves no transfer. The box is cut in memory once and saved locally, so later reads never touch the cloud again.
ARCO-ERA5, geopotentialOne hour × 37 levels × the whole globeEach hour of Z500 costs a full 37-level chunk. Blocking is a daily index, so Z500 is read every 6 hours instead of hourly, which cuts transfer by six. Blocking studies also have a Z500-only loader, so they don't download wind fields they don't need.
ARCO-ERA5, time axisPadded to 2050; the real end is in valid_time_stopRequests past the real end are rejected at once, instead of silently returning empty or fill values.
EERIE gr025 (planned)Flattened 1,038,240-point grid, chunks of 3 times × 3 levels × globe, 6-hourly, no 100 m windThe loader will roll the grid back to latitude and longitude and cache once. It will use the 1000 hPa wind as a hub-height proxy and flag points where that level lies underground.
SMARDOne JSON file per week per filter and zone, with an index listing the weeksThe pipeline reads the index first and fetches only the weeks that overlap the request. Each weekly file is cached as Parquet, so nothing is downloaded twice.

3. Problems the pipeline had to solve

undocumented API

Finding the capacity series

SMARD's installed-capacity filter ids (186, 187, 188) are not in its public API spec. They were identified by matching Germany-wide yearly values against known capacity, for example 2024: 59.8 GW onshore, 8.5 GW offshore, 76.6 GW solar.

missing ≠ zero

Offshore wind in inland zones

The endpoint returns 404 for offshore wind in Amprion and TransnetBW, which have no coastline. The client turns this into an explicit zero series, but any other 404 still stops the run with an error, so a real gap cannot pass as zero.

units

Energy versus power

SMARD reports energy per interval (MWh) and ERA5 stores solar radiation as accumulated J m⁻² per hour. Both are converted to mean power, MW and W m⁻², and small negative night-time values are set to zero.

time

Time zones and weeks

SMARD's weekly files start at local midnight and shift with daylight saving time. All times are converted to UTC. The last file in the index gets a week plus one hour, so a daylight-saving week is not cut short. Windows are half-open [start, end) throughout.

reliability

Retries that know when to stop

Requests retry with exponential backoff on rate limits (429), server errors and time-outs. They give up straight away on other client errors, which a retry would not fix, and a short pause between weekly downloads keeps the load on the public server low.

caching

No stale caches

The ERA5 cache key holds the time window, the box and the Z500 stride, so a different request can never read an old file. The store's encoding is cleared before writing, so the cloud's one-hour chunks are not copied into the local store.

fair comparison

One contract for every source

Dimension order, coordinate direction, longitude range, variable names and units are checked by one function at every loader exit. A source that breaks the contract fails loudly before any diagnostic runs.

honesty

Biases reported, not tuned away

The wind-to-power model is deliberately simple. Its losses sit in one explicit factor that is reported, never fitted to SMARD, so the mismatch with the observations is shown as a result in itself.

4. How the code is organised and checked

SafeguardWhat it does
51 offline tests (pytest)They cover the contract rules, SMARD week selection, the 404-to-zero rule and caching, ERA5 normalisation and cache keys, the power curve, blocking detection and Dunkelflaute event counting. Each test runs on small made-up data with a known answer.
Network blocked in tests (pytest-socket)No test can reach the internet. A test that tried to would fail, so the suite is fast and gives the same result anywhere.
Continuous integration (GitHub Actions)Every push and pull request installs the package, runs ruff lint and format checks, then the tests.
Build phases with gatesEach phase (scaffold, SMARD, ERA5, transfer, diagnostics, dashboard, EERIE, projection) has a check it must pass before the next one starts.
Packaged and pinnedpyproject.toml makes the code an installable package with pinned version ranges, and environment.yml rebuilds the same setup.

6. In one sentence

Reanalysis data are read anonymously from a public cloud Zarr store and grid-operator data from a REST API. Both are retried, converted to one tested dataset contract and cached as Zarr and Parquet, so each byte is downloaded once. The same diagnostics then run on any source that meets the contract, which is what will allow a fair test of the EERIE model against reanalysis.
